# HRX 0.11 migration

CLEF pins `hrx-rs = 0.11.0`, including native HRX `61c152ac4b` and libamdf
ABI 10. Cargo resolves the published crate; no sibling checkout or local patch
is required. Converted checkpoint weights remain compatible.

## Features used

- The updated native compiler/runtime applies to every kernel. Existing tiled
  BF16 GEMM, packed INT4 WMMA, shared attention and graph replay remain in use.
- Loom alignment predicates use `multiple_of` in production and benchmark
  sources, replacing the retired `mul` spelling.
- `CLEF_COMPILE_REPORT_DIR` now exports cached target assembly alongside resource
  reports. The new listing API makes register movement, memory waits and WMMA
  instructions inspectable without extracting code objects manually.
- Omni route grouping uses workgroup prefix scans and reductions. Each lane
  searches one token's eight selected experts, then writes its ordinal at an
  exclusive prefix offset. Token order and the existing expert-table layout are
  preserved. Grouping is reused by all three expert projections.
- Register packing uses a bank of eight-element vectors, allowing the compiler
  to split the retained values into supported register fragments. Packing loops
  are explicitly unrolled so integer code extraction has constant indices.
  This preserves the fused RMSNorm, attention-gate and SwiGLU packing paths.

Workgroup collectives were already available in Loom; 0.11 additionally exposes
them through the C++ importer. CLEF uses its existing Loom sources directly.

The original wide register vector exceeded the new compiler's carrier limit;
dynamic integer extraction also lowered to an unsupported table lookup. Both
were caught by the existing GPU tests, without changing accuracy tolerances.
A separate lifetime test had supplied row-major weights to the tiled loader;
its failure reproduced on 0.10.1. Its fixtures now match the loader contract,
while the independent CPU oracle still uses logical weight rows.

## Validation and performance

Omni INT4 warm resident throughput measured **496.2 and 521.9 input tok/s** in
two complete seven-request runs, versus 520.3 on the earlier 0.10.1 build.
Text measured 752.0 and 735.2 tok/s. All 14 outputs reproduce exactly across
the two model loads. Peak engine allocation remains 17.7 GiB.

Including both requests of every pair gives 367.0 and 418.6 tok/s, versus 461.8
previously. These totals include first-shape preparation and compilation, which
varied substantially. All measurements use the shared GPU and exclude model
loading. The evidence supports roughly unchanged warm whole-model throughput,
not an overall upgrade speedup. The second run is 6.9× the original 75.7 tok/s
scalar expert implementation. The README now reports subsequent full JevBench
measurements, linked below.
[Raw outputs, timings, compiler identity and validation records](results/hrx-011-20261015.json).

The paired routing benchmark measures **205.3 → 15.5 µs (13.24×)** at 256
tokens with balanced expert selection, and **244.2 → 15.1 µs (16.14×)** with
concentrated selection. Single-token cases are effectively unchanged. All 14
routing cases pass exact comparisons, including three changed-input replays.
These are routing dispatch measurements, not whole-model speedups.

All 32 expert cases pass the existing BF16/INT4 checks. GPU operator coverage
includes CLEF and Flash attention, DeltaNet, dense GEMM, normalization, fused
packing, memory lifetimes, Omni routing and media operators. Stable Rust and
Rust 1.91 pass CPU tests and Clippy; the 36 Python evaluation-tool tests pass.

The seven Omni INT4 smoke requests still match all nine Cloudflare oracle
choices. Repeated requests are exact within the new build, but the compiler
upgrade changes probabilities by up to 0.08994 versus 0.10.1. Full BF16 text and
audio/video validation passes with maximum oracle errors of 0.000622 and
0.005157, respectively. These streamed BF16 checks use at most 2.26 GiB of
engine allocations and do not measure resident throughput. Subsequent full
JevBench results are in [Omni memory tuning](omni-memory-tuning.md);
WorkflowEvals qualification remains pending.

## Features reviewed

The new virtual reservations, remapping and external GPU pointers are useful for
engines that move backing behind stable addresses. CLEF currently owns resident
weights and graph-bound scratch; changing that ownership needs a separate memory
design and would not itself accelerate these kernels.

Automatic idle unloading applies to registered managed models. CLEF's CLI keeps
one explicitly loaded model alive while processing requests. It does not opt into
unloading between requests. C++ preambles and math-policy controls do not apply to
the native Loom source path. Numerical policy remains unchanged.

The new AQL dispatch timestamps and shared clock queries complement the PM4
graph profiling already used here. CLEF retains PM4 graph batching and its native
timestamp frequency rather than switching queue engines for timing. NPU trace
controls and command arrays apply to XDNA workloads; CLEF runs on the GPU.

Subsequent [expert-load and attention experiments](omni-memory-tuning.md)
retain this result as their numerical reference.

## Reproduction

```sh
cargo +stable build --release --locked --features bench-internals \
  --bin clef --example profile_inference
cargo +stable bench --locked --features bench-internals --bench omni --no-run
cargo +stable test --locked --lib --all-features --no-run
```

Run the printed test executable under the memory guard, selecting
`omni::tests::grouped_routes_match_cpu --ignored --exact --nocapture`.
This checks exact counts and ordered ordinals for 1, 17, 64, 65, 128, 255 and
256 tokens, with three different inputs replayed through each graph, including
empty and fully populated experts.

For compiler reports, set `CLEF_COMPILE_REPORT_DIR` on that command. Repeat with
a fresh guard output directory to exercise cached listing retrieval. The ordinary
Omni expert benchmark checks both precisions, both projection shapes, balanced
and concentrated routes, and changed-input replay. See
[Omni kernel tuning](omni-kernel-tuning.md) for full-model qualification commands.

The same benchmark includes a paired serial/parallel routing group. To measure
only routing, without constructing expert weights:

```sh
CLEF_BENCH_OMNI_FILTER=routes/ python3 scripts/memory_guard.py \
  --output artifacts/omni-routing-bench --memory-gib 4 -- \
  cargo +stable bench --locked --features bench-internals --bench omni
```

Each pair alternates execution order. Fixture creation and correctness reads
are outside timing; graph submission and completion are included. The benchmark
checks counts and populated ordinals after three changed-input replays before
timing, ignoring unused table entries.
